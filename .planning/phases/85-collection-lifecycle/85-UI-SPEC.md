Traced from the rendered tree (not the dead `CollectionView.tsx`/`WatchCard.tsx`/`StatusToggle.tsx` island — see `project_watchdetail_dead_island` lesson, confirmed dead again in 85-RESEARCH.md):

- `src/components/watch/AddWatchFlow.tsx` (`handleMoveToCollection`) and `WatchDetailHero.tsx`'s edit-save path — both gain the celebration trigger (confetti + distinct toast) fired immediately before their existing `router.push`, gated on a server-returned `promoted` signal.
- New: `src/lib/celebrate.ts` — confetti + `prefers-reduced-motion` wrapper (no new UI component, but its call sites are part of this contract).

## Spacing Scale

Declared values (must be multiples of 4), matching the project-wide convention already visible in `ProfileWatchCard`/`CollectionTabContent`/`WatchDetailHero`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps inside chips/badges, badge inner padding (`px-1`, `gap-1`) |
| sm | 8px | Row internal gaps (`gap-2`), toggle-chip icon gap, dialog field label-to-input gap (`space-y-2`) |
| md | 16px | Default card padding (`p-4`/`px-3 py-2`), dialog section gaps (`space-y-4`/`gap-4`) |
| lg | 24px | Dialog outer section spacing (`space-y-6`, matches `ConfirmStep`), grid-to-toolbar gap on the Collection tab |
| xl | 32px | Not used on this phase's surfaces |
| 2xl | 48px | Not used on this phase's surfaces |
| 3xl | 64px | Not used on this phase's surfaces |

Exceptions:
- Every tappable control resolves to a **44×44px minimum hit area**: the ⋯ menu trigger (`min-h-[44px] min-w-[44px]`, matching `WearOverflowMenu`), the toggle chip, and every reason-radiogroup button (matches `ConfirmStep`'s `min-h-[44px]` radio buttons) all carry this floor.
- Native `<input type="date">` and the price `<input type="number">` in the disposal dialog use `text-base md:text-sm` (16px floor) to avoid iOS Safari auto-zoom, matching the project's established iOS input convention.

## Typography

Matches the project's established 2-weight system (no `font-medium`/500 or `font-bold`/700 introduced in new code):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / row text, dialog body copy | 14px (`text-sm`) | 400 regular (`font-normal`) | 1.5 |
| Label / emphasis (dialog field labels, watch name, menu items) | 14px (`text-sm`) | 600 semibold (`font-semibold`) | 1.5 |
| Micro / meta (reason·date badge, helper text, disposal-field hints) | 12px (`text-xs`) | 400 regular (`font-normal`), `text-muted-foreground` | 1.5 |
| Dialog title | 16px (`text-base`) | 600 semibold (`font-semibold`) | 1.2 |

Rules:
- Dialog title, radiogroup section label ("Reason"), and the toggle-chip label use `font-semibold`.
- Badge/helper/error copy uses `font-normal`.
- No `font-medium` or `font-bold` in any newly written JSX for this phase (shadcn base `Button`/`DropdownMenuItem` internals are left as-is).

## Color

Matches the existing OKLCH token set in `src/app/globals.css` (warm neutral base + amber/gold accent) — no new tokens introduced:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-background` (`oklch(0.985 0.003 75)` light / dark equivalent) | Page background, Collection tab wrapper |
| Secondary (30%) | `bg-card` / `bg-muted` (`oklch(1 0 0)` / `oklch(0.95 0.005 75)` light) | Card surfaces, dialog content, reason·date badge background |
| Accent (10%) | `bg-accent` / `text-accent-foreground` (`oklch(0.76 0.12 75)` light) | **Reserved for exactly: (1) the selected reason button in the disposal-reason radiogroup, (2) the "Show previously owned" toggle chip's ON state, (3) the existing `FilterChips` active role-tag chip (unchanged).** Never used for the dialog's primary submit button, the ⋯ menu trigger, or the reason·date badge — those use `variant="default"`/muted tokens respectively. |
| Destructive | `text-destructive` / `role="alert"` | Disposal-dialog future-date validation error and generic submit-error banner only (matches `LogTodaysWearButton`'s existing error pattern). NOT used for the "Mark as previously owned" menu item or dialog submit button — this action is reversible (D-04) and is not styled as destructive. |

Every `bg-accent` override on an `outline`-variant button (the radiogroup buttons) MUST pair with an explicit `dark:` variant, copying `ConfirmStep`'s exact class list verbatim:
```
'border-accent bg-accent text-accent-foreground hover:bg-accent hover:text-accent-foreground
 dark:border-accent dark:bg-accent dark:text-accent-foreground dark:hover:bg-accent dark:hover:text-accent-foreground'
```
The toggle chip reuses `FilterChips`' existing active/inactive classes verbatim (`bg-accent text-accent-foreground border-accent` / `bg-background text-muted-foreground border-border`) — both already resolve correctly per-theme via CSS variables, no new `dark:` pairing needed there.

**Muted/dimmed previously-owned card treatment is NOT a color-token change** — it is an `opacity-60` applied to the whole `<Card>` (not just the image), so the brand/model text, badge, and image all dim uniformly in both themes without introducing a new muted-surface token. Do not use `grayscale` or a raw hex overlay.

## Interaction Contract

### ⋯ overflow menu on `ProfileWatchCard` (LIFE-03, D-05)
- Component: `DropdownMenu`/`DropdownMenuTrigger`/`DropdownMenuContent`/`DropdownMenuItem` from `src/components/ui/dropdown-menu.tsx`, mirroring `WearOverflowMenu.tsx` almost verbatim.
- Trigger placement: **top-right corner of the image area**, `absolute top-2 right-2 z-10`, `inline-flex items-center justify-center min-h-[44px] min-w-[44px]`, icon `MoreHorizontal` (lucide, `size-5`). This corner is unused today by owner cards (the like/comment overlay chips only render for `!isOwner`; owners see a static count line inside `CardContent` instead) — no collision.
- Trigger MUST call `e.preventDefault(); e.stopPropagation()` on click, identical to the existing like/comment chip guards in the same file (Pitfall 1 in 85-RESEARCH.md) — otherwise the click bubbles into the card's `<Link>` and navigates instead of opening the menu.
- Owner-only (`isOwner === true`); never rendered for a visitor.
- Menu contents: on an `owned` card, exactly one item — "Mark as previously owned" (opens `MarkPreviouslyOwnedDialog`, does not itself submit). On a `previously_owned` card, exactly one item — "Edit" (`render={<Link href={`/w/${watch.id}/edit`} />}`).
- `MarkPreviouslyOwnedDialog` is rendered as a **sibling to the `<Link>`** in `ProfileWatchCard`'s returned fragment (same placement as `WatchCommentSheet`), controlled by lifted `useState` — never nested inside the menu's own DOM subtree, per Pitfall 2 (menu-close would tear the dialog down mid-interaction otherwise).

### Disposal dialog (LIFE-03, D-06/D-07)
- Field order top to bottom: Reason (radiogroup, required) → Disposal date (optional) → Amount received (optional) → error slot → footer (Cancel / Mark as previously owned).
- Reason radiogroup: hand-rolled WAI-ARIA `role="radiogroup"` + roving-tabindex, copied from `ConfirmStep.tsx`'s `handleKeyDown` pattern (arrow keys / Home / End cycle the 5 reason buttons) — do NOT introduce a new generic `RadioGroup` primitive; none exists in `src/components/ui/` and the project has already solved this pattern twice (Phase 68, Phase 82).
- All three fields render unconditionally regardless of which reason is selected (D-06 — "no reason-specific hiding").
- Date input `max` uses the client's own `todayLocalISO()`; the Server Action independently re-validates using the `isPlausibleClientToday` + lexical-string-compare pattern from `wearEvents.ts` (Pitfall 4) — never a server-computed "today".
- Presentation: `Dialog` (not `Sheet`) at all breakpoints, matching every other watch-mutation dialog in this codebase (`WatchDetailHero`'s delete dialog, `LogTodaysWearButton`).

### Muted card + reason·date badge, CSS chain (LIFE-05, D-16) — explicit per `feedback_ui_spec_css_chain_blind_spot`
This phase reuses `ProfileWatchCard`'s existing `isWishlistLike` conditional pattern, which currently gates the wear badge and wear line. Extend it with a parallel `isPreviouslyOwned = watch.status === 'previously_owned'` flag and apply exactly these changes — do not let `previously_owned` fall through the existing `!isWishlistLike` branches unmodified, or a previously-owned card will incorrectly show a "Worn today"/"Not worn recently" badge and a wear line, colliding with the new reason·date badge:
1. **Card opacity**: `<Card className={cn(..., isPreviouslyOwned && 'opacity-60')}>` — applied to the whole `Card`, not the image div alone, so text and badge dim uniformly.
2. **Top-left overlay swap**: when `isPreviouslyOwned`, render the reason·date badge (`absolute top-2 left-2 z-10 rounded-full bg-background/90 px-2 py-0.5 text-xs font-normal text-muted-foreground shadow ring-1 ring-border`) INSTEAD of the existing wear badge (`isWornToday`/`isStale`) — the two are mutually exclusive states on the same corner, gated by `isPreviouslyOwned ? <ReasonDateBadge /> : (!isWishlistLike && (isWornToday || isStale) && <WearBadge />)`.
3. **Wear line suppression**: change the existing `{!isWishlistLike && <p>{lastWornLabel}</p>}` condition to `{!isWishlistLike && !isPreviouslyOwned && <p>{lastWornLabel}</p>}` (D-16 — "no wear... actions on these cards"; the static "Worn Xd ago" line reads as an active-collection affordance and must not appear).
4. **Price line unchanged**: `previously_owned` is not wishlist-like, so `primary = watch.pricePaid`, label "Paid" — this still renders (`Paid: $X`) since historical purchase price is informational, not an "action."
5. **Like/comment overlay chips unaffected**: already gated on `!isOwner`; a previously-owned card is only ever owner-visible (D-13), so this block never renders regardless.
6. **⋯ menu stays visible** at `top-right` on previously-owned cards (per D-16 — "owner's ⋯ menu stays"), now offering "Edit" instead of "Mark as previously owned".
7. **z-index**: both the reason·date badge (top-left) and the ⋯ menu trigger (top-right) sit at `z-10`, above the `object-cover` image (`z-0` implicit) but do not overlap each other — no stacking-order ambiguity to resolve.

### "Show previously owned" toggle (LIFE-05, D-15)
- Placement: a chip-styled `<button>` appended immediately after `FilterChips`' role-tag chips and before the search `Input`, inside the same `flex items-center gap-2` toolbar row — NOT a new `Switch` primitive (none exists in `src/components/ui/`; introducing one is out of scope).
- Visual classes: reuse `FilterChips`' own active/inactive class strings verbatim (`bg-accent text-accent-foreground border-accent` ON / `bg-background text-muted-foreground border-border` OFF), so the toggle reads as visually consistent with — but is functionally independent of — the role-tag chip row. Add a `ml-2` gap (or a `border-l pl-2` divider) before it so it doesn't visually blend into the role-tag group.
- State: plain `useState<boolean>(false)` inside `CollectionTabContent` — **not persisted** (D-15 — resets to off every visit, no localStorage/URL param).
- Owner-only: the toggle itself is never rendered when `!isOwner` (non-owners never receive `previouslyOwnedWatches` data at all per D-13, so there is nothing to toggle).
- Filtering: when ON, `previouslyOwnedWatches` are appended to the end of the `activeChip`/`search`-filtered `ownedWatches` list (same role-tag and search-text filters apply to both arrays identically — a search for "Omega" should surface a previously-owned Omega too). Previously-owned cards are always sorted after all owned cards in the resulting grid, never interleaved by date.
- **Empty-state gating fix (required, not explicit in CONTEXT — closes a real gap)**: the existing `if (watches.length === 0)` early-return in `CollectionTabContent` must be re-evaluated against `ownedWatches.length === 0 && previouslyOwnedWatches.length === 0` (owner) — an owner who has disposed of their only watch must still see the toolbar + toggle (not the "Nothing here yet" full empty-state) so they can reach their previously-owned history. Only show the "Nothing here yet" empty-state when both arrays are empty for the owner, or when the single non-owner-visible array is empty for a visitor.

### Edit form status dropdown (LIFE-03, D-07)
- `WatchForm`'s status `<Select>` filters `WATCH_STATUSES` to exclude `previously_owned` UNLESS `watch?.status === 'previously_owned'` (i.e., you can never manually dispose of a watch through the edit form — only through the dialog — but you CAN see/change the status of an already-disposed watch here).
- When the current or newly-selected status is `previously_owned`, render the same three disposal fields (Reason/Disposal date/Amount received) inline below the status `<Select>`, using identical field components/labels as `MarkPreviouslyOwnedDialog` (do not fork a second copy of the field markup — extract a shared fields subcomponent if the planner judges it worthwhile).
- When the user changes status away from `previously_owned` in this form, show the helper text **"Changing status will clear the disposal details recorded above."** beneath the `<Select>` (D-04 undo path) — no separate confirmation dialog.

### Promotion celebration (LIFE-04, D-09/D-10/D-11)
- Trigger point: fire `fireConfettiIfAllowed()` (skips under `prefers-reduced-motion`) + `toast.success(...)` in the SAME client component that already awaits the Server Action result, **immediately before** the existing `router.push(dest)` call in both `AddWatchFlow.handleMoveToCollection` and `WatchDetailHero`'s edit-save handler — never on a destination-page mount effect (Pitfall 3 / Router Cache stale-instance gotcha).
- Toast copy branches on the server-returned `promotedFrom`: `'grail'` → "Grail acquired!"; otherwise → "Added to your collection!". Both are visually the standard `toast.success` style (green check icon per sonner default) — no new toast variant needed, only the copy differs from the existing "Moved to collection" toast so the two are distinguishable side-by-side in a session.
- Confetti call: `confetti({ particleCount: 100, spread: 70, origin: { y: 0.6 } })`, default `canvas-confetti` palette (no brand-color override required — Claude's discretion, low risk either way).
- No modal, no price-paid prompt, no photo-link CTA in the toast (D-12 — "pure celebration, asks for nothing"). The toast's action button (if any) stays limited to the existing "View" action already present in the "Moved to collection" toast pattern — do not add new actions to the celebration toast.
