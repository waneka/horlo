<objective>
WEAR-02 (server half): add a `logBackfillWear` Server Action. It logs a photo-less wear on any past or current date with a note and visibility, rejects future dates on the server, turns the duplicate-day constraint into a friendly error, and writes feed activity only for wears dated today.

Purpose: this is the single write path behind the unified "Log a wear" form (built in 84-04). It is a dedicated action rather than an extension of `markAsWorn` because `markAsWorn` uses `logWearEvent`, whose `onConflictDoNothing` swallows duplicates and still logs activity (RESEARCH Pitfall 6). Following `logWearWithPhoto`'s explicit insert plus 23505 catch avoids that bug by construction. `markAsWorn` is left untouched because the new path does not use it (CONTEXT discretion).
Output: `logBackfillWear` export plus the `tests/actions/wearEventsBackfill.test.ts` contract suite.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → logBackfillWear Server Action | Untrusted watchId, wornDate, today, note, visibility cross here |
| Server Action → wear_events / activities tables | Writes scoped to the authenticated user.id |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-84-IDOR | Tampering / Information Disclosure | logBackfillWear watchId | mitigate | `watchDAL.getWatchById(user.id, watchId)` runs before any write and returns the uniform 'Watch not found' on miss. The insert carries server-side `user.id`, never a client user id. Covered by test T4. |
| T-84-DATE | Tampering | logBackfillWear wornDate/today | mitigate | Zod regex plus calendar-validity refine on both dates, then a server-side `wornDate > today` rejection that does not trust the client `<input max>`. Covered by tests T2 and T3. |
| T-84-DUP | Tampering / DoS (minor) | concurrent duplicate submissions | mitigate | The `wear_events_unique_day` DB constraint is the backstop. The explicit 23505 catch returns the friendly error and no activity is logged (not onConflictDoNothing). Covered by test T7. |
| T-84-MASS | Elevation of Privilege | extra input keys (photoUrl, id) | mitigate | `.strict()` zod schema rejects unknown keys. The wear id is generated server-side with `crypto.randomUUID()` and photoUrl is hard-coded null. Covered by test T2. |
| T-84-ACT | Repudiation / Tampering | client lies about `today` to force or suppress activity | accept | The client-supplied-today trust model is the project invariant (260622-exo) shared by markAsWorn and logWearWithPhoto. Impact is limited to the caller's own feed entries for their own watches. |
| T-84-XSS | Tampering | note text | accept | The note is length-capped at 200 and rendered as React text nodes (auto-escaped) everywhere it appears. No HTML sink. |
</threat_model>
